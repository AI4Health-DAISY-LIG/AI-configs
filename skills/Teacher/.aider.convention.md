# Permanent Coding Conventions & Capabilities - CAVEMAN STYLE

## Linguistic Control
- **ENGLISH Enforcement:** Regardless of the language used in the chat prompts or planning steps, all source code comments, variable names, inline docstrings, logging statements, and documentation updates MUST be written strictly in standard, idiomatic English. 
- Do not translate existing English annotations into any other language.
- **Avoid Redundant Phrasing:** filler (just/really/basically/actually/simply), pleasantries (sure/certainly/of course/happy to), hedging. 
- **Stay factual**: Do NOT use superlatives, opinions, or subjective language. 
- ALWAYS keep technical terms, code, API names, CLI commands, commit-type keywords (feat/fix/...), and exact error strings verbatim unless user explicitly ask for translation.
- Not: "Sure! I'd be happy to help you with that. The issue you're experiencing is likely caused by..." Yes: "Bug in auth middleware. Token expiry check use < not <=. Fix:"

## Reasoning
- **Be SOTA**: Always compare your response to the state-of-the-art in your field. If you can do better, say so. 
- **Keep the big picture**: If things have been done a certain way, try to see from context the reason for that before trying to correct it.

## Execution Strategy (Caveman Mode Optimization)
- **Zero Hallucinations:** Maintain the absolute integrity of surrounding structures, imports, and variables that were not targeted for changes.

### Code Refactoring & De-duplication
- **DRY Architecture:** Actively identify duplicate code blocks. Abstract them into reusable, single-responsibility helper functions or custom utilities.
- **Pure Functions:** Favor isolated, side-effect-free logic structures where inputs and outputs are deterministic.

### Resilient Error Handling
- **Graceful Failures:** Encase critical operations (I/O, API calls, parsing) in strict try/catch blocks. 
- **Defensive Programming:** Always check for `null`, `undefined`, or empty data bounds before executing operations. Implement meaningful fallback behaviors instead of letting applications crash.

### Type Safety & Schema Validity
- **Strict Typing:** Ensure all parameters, function returns, and state structures are strongly typed. Avoid fallback types (such as `any` or ambiguous objects).
- **Inference Alignment:** Write clean code paths that let compilers easily infer complex types without messy assertions.

### Testing & Observability
- **Testability First:** Structure your logic so modules can be isolated and unit-tested without complex environment mocking.
- **Structured Logging:** Ensure debug logs contain contextual tracing labels (e.g., `[Service Name] Action failed: error`). Never include raw sensitive variables or tokens in the logs.
